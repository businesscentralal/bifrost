# Install and upgrade

Most Bifröst apps replace a published Origo Cloud Events app. The successor is a **new
app** with a new id and a new object ID range, installed side by side with the app it
retires. On first install it takes that app's data over; the old app is deprecated
afterwards.

This page describes that take-over pattern, and the other work an install codeunit does.

## The take-over pattern

The take-over runs from `OnInstallAppPerCompany`, before anything else the app installs,
and it is driven by a list of `(old table id, new table id)` pairs. For each pair:

1. **Check the old table still exists** — `TableMetadata.Get(<old table id>)`. The
   published app may not be installed in this company at all.
2. **Skip when the new table already has rows** — `if not Target.IsEmpty() then exit;`.
   This is what makes the take-over idempotent and safe on reinstall.
3. **Copy with `DataTransfer` on identical field numbers.** The successor keeps the
   predecessor's field numbering, so every pair is `AddFieldValue(N, N)`.
4. **`DataTransfer.UpdateAuditFields(false)`** so `SystemModifiedAt` and
   `SystemModifiedBy` survive the copy — the rows keep their original audit trail.
5. **Log the result**, so an administrator can see what moved.

From Nornir's `App Takeover ori`:

```al
/// <summary>Copies <c>CE Orchestrator Setup ori</c> (10076036) into <c>Scheduler Setup ori</c> (10035536).</summary>
local procedure TakeOverSchedulerSetup()
var
    Target: Record "Scheduler Setup ori";
    OldRef: RecordRef;
    DataTransfer: DataTransfer;
begin
    if not OldTableExists(10076036) then
        exit;
    if not Target.IsEmpty() then
        exit;
    DataTransfer.SetTables(10076036, Database::"Scheduler Setup ori");
    OldRef.Open(10076036);
    if OldRef.FieldExist(10) then
        DataTransfer.AddFieldValue(10, 10);
    if OldRef.FieldExist(20) then
        DataTransfer.AddFieldValue(20, 20);
    if OldRef.FieldExist(30) then
        DataTransfer.AddFieldValue(30, 30);
    OldRef.Close();
    DataTransfer.UpdateAuditFields(false);
    DataTransfer.CopyRows();
    LogTakeOver('Scheduler Setup ori', Target.Count());
end;

local procedure OldTableExists(OldTableId: Integer): Boolean
var
    TableMetadata: Record "Table Metadata";
begin
    exit(TableMetadata.Get(OldTableId));
end;
```

The `FieldExist` guard around every `AddFieldValue` is not decoration. The published app's
schema is not guaranteed to be byte-identical across environments — two containers running
the same declared version have been observed with different package ids — and
`DataTransfer` fails hard on a field that is not there. Checking each field first turns a
failed install into a partial copy.

Nornir's take-over is generated by a script from the migration name map, not typed by hand,
and the codeunit says so in its summary. That is the right approach once an app has more
than a couple of tables: the field lists are long and mechanical.

### Which tables are copied — and which are not

**Copied**: everything the customer configured or authored. Setup singletons, connection
and credential records, scheduled entries, recurring templates, playbooks and their steps
and conditions, saved report presets, per-user settings.

**Not copied — transient tables:**

- `Message ori` — the message queue.
- `Message Argument ori` — the per-call argument record.
- `Request Log ori` — outbound request logging.
- Buffer and working tables.
- Execution logs. Nornir explicitly leaves `Playbook Instance ori` and
  `Playbook Step Log ori` behind; Hnitbjörg leaves upload sessions and their chunks behind.

These are in-flight or historical rows with no configuration value. Copying them would
migrate noise, and in the case of the request log it would move already-masked payloads
into a new table for no benefit.

### The three complications

**BLOB fields.** `DataTransfer` does not support them. Copy them afterwards with a
`RecordRef` pass: walk the new table, find the matching row in the old table by primary
key, and move each BLOB through a `Temp Blob`.

```al
BlobFieldNos.Add(30);
CopyBlobFields(10076039, Database::"Playbook ori", BlobFieldNos);
```

**Values that carried an object id or an enum ordinal.** A row that stored
`Object ID to Run` or a `Message Type` ordinal from the predecessor's range holds a number
that means nothing in the new range. Shift it by the range offset after the copy:

```al
ShiftIntegerField(Database::"Scheduled Entry ori", Target.FieldNo("Object ID to Run"), 10076035, 10076134, -40500);
```

Only values inside the old range are shifted; anything else is left alone.

**Permission set assignments.** A user who held the old app's permission set does not
automatically hold the new one — the assignment is keyed by app id. Walk `Access Control`
for each old role id under the old app id and insert the matching row for the new role id
under the current app id:

```al
local procedure TakeOverAccessControl()
var
    Migrated: Integer;
begin
    Migrated += MigrateRole('CE Orchestrator ori', 'BIFROST Nornir ori');
    Migrated += MigrateRole('CE Orch. Setup ori', 'BIFROST NrnSetup ori');
    if Migrated > 0 then
        LogTakeOver('Access Control', Migrated);
end;
```

### Ordering

The take-over must run **before** the app creates its own singletons. Nornir's install
codeunit is explicit about it:

```al
trigger OnInstallAppPerCompany()
var
    SchedulerSetup: Record "Scheduler Setup ori";
    JobQueueManagement: Codeunit "Scheduler Mgt ori";
    AppTakeover: Codeunit "App Takeover ori";
begin
    // The take-over must run before the setup singleton is created, otherwise the target table
    // is no longer empty and the published app's setup would not be copied.
    AppTakeover.TakeOverAll();
    SchedulerSetup.OnOpenEmptyRec();
    JobQueueManagement.RegisterJobQueues();
    RegisterRetentionPolicies();
end;
```

Insert your setup record first and the "skip when the target is not empty" test fires
against a row you just created yourself, and the customer's configuration is silently left
behind.

Hnitbjörg puts its take-over in its own `Subtype = Install` codeunit instead of calling it
from another one. Either arrangement works; what matters is that no other install work
touches the target tables first.

## What else an install codeunit does

Beyond the take-over, `OnInstallAppPerCompany` is where an app registers itself with the
platform and with Foundation.

**Retention policies** for any log table the app writes:

```al
local procedure RegisterRetentionPolicies()
var
    RetenPolAllowedTables: Codeunit "Reten. Pol. Allowed Tables";
begin
    // field 30 = "Started At" on Playbook Instance ori; min 28 days
    RetenPolAllowedTables.AddAllowedTable(Database::"Playbook Instance ori", 30, 28);
    RetenPolAllowedTables.AddAllowedTable(Database::"Playbook Step Log ori");
end;
```

**ChangeLog guard exceptions.** Foundation's ChangeLog Write Guard blocks writes to
change-logged fields through the Data API. A table your own app maintains needs an
exception, registered through the public procedure on the setup record:

```al
local procedure RegisterChangeLogGuardExceptions()
var
    BifrostSetup: Record "Setup ori";
begin
    if not BifrostSetup.Get() then
        exit;
    BifrostSetup.AddChangeLogGuardException(Database::"Storage Attachment Link ori", 0);
end;
```

Field number `0` covers the whole table. `AddChangeLogGuardException` inserts only when the
exception is not already there, so it is safe to call on every install.

**Assisted setup**, when the app has a wizard, through `Guided Experience.InsertAssistedSetup`
under `"Assisted Setup Group"::Extensions`.

**Secret registration** — see [Setup and secrets](/extensibility/setup-and-secrets).

**Upgrade tags.** Hnitbjörg sets an initial-release tag from install and registers it on
`OnGetPerCompanyUpgradeTags`, so a later data upgrade can tell a fresh install from an
upgraded one:

```al
internal procedure GetInitialReleaseTag(): Code[250]
begin
    exit('Origo.Bifrost.Hnitbjorg-Initial-20260905');
end;
```

## The upgrade codeunit

A `Subtype = Upgrade` codeunit handles versions after the first. Two triggers do the work:

- `OnCheckPreconditionsPerCompany` — verification and re-registration that must happen
  before the upgrade runs.
- `OnUpgradePerCompany` — the data upgrade itself.

Anything registered at install is registered again at upgrade, because a company that
upgrades never runs the install trigger. Nornir's upgrade codeunit repeats the setup
singleton creation, the retention policy registration and the HTTP client enablement for
exactly that reason.

```al
codeunit 10035538 "App Upgrade ori"
{
    Access = Internal;
    Subtype = Upgrade;

    trigger OnUpgradePerCompany()
    begin
        CreateJobqueueOrchestratorSetup();
        SetDefaultTypeToCodeunit();
        EnableHttpClientRequests();
        RegisterRetentionPolicies();
    end;
}
```

Keep upgrade steps idempotent and guarded — `if IsEmpty() then exit;` before a `ModifyAll`,
`if not HasUpgradeTag(...)` before a one-time migration. An upgrade trigger can run more
often than you expect.
